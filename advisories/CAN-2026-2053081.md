# Exported FileProvider in Ghost Commander opens caller-named paths with a caller-chosen access mode

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053081` |
| **Package** | `com.ghostsq.commander` |
| **Product** | Ghost Commander |
| **Affected versions** | 479 (affected) |
| **Weakness** | CWE-22 (Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H48-01 |

## Summary

Ghost Commander (com.ghostsq.commander) version 479 for Android: an exported permission-less provider that turns a caller-supplied path into a file descriptor opened with a caller-supplied access mode, so any app can read and write any file the file manager's uid can reach - measured as a create-on-write plus read-back inside Ghost Commander's own private data directory Impact ceiling: Ceiling: the measured crossing is Ghost Commander's own private storage (`/data/data/com.ghostsq.commander/files/`, create-on-write + read-back); SAF-granted trees and credential-bearing remote shares are capability, not measurement (none was configured on either guest); a `/sdcard/Download/` arm is recorded as a negative (`EACCES` raised inside GC's own `open`, logged under GC's `FileProvider` tag) because that guest's GC lacks storage access there - a property of the guest's grants, not a guard in the code; the provider cannot list directories and its `insert`/`update`/`delete` are no-ops, so the write comes from `openFile`'s caller-supplied mode rather than from the row API; no code execution and no privilege escalation are claimed (the primitive is read/write on files reachable by the file manager's uid - for example replacing the app's own configuration or its stored credentials, which the class keeps under `FileProvider`'s name)

## Attack vector and prerequisites

Precondition: no runtime permission, no user interaction, no prior state; the caller needs the authority literal and, on Android 11+, visibility of the target package - a free `<queries>` declaration (no permission, no consent) which the probe carries while otherwise holding only `INTERNET`

## Proof of concept

Artifact read with `aapt2 dump xmltree --file AndroidManifest.xml` on the installed APK: the `E: provider (line=218)` block carries `android:name="com.ghostsq.commander.FileProvider"`, `android:exported="true"`, `android:authorities="com.ghostsq.commander.FileProvider"` and no permission attribute of any kind (the sibling `StreamProvider` is exported the same way, while `DocumentsProvider` *is* wrapped in `android.permission.MANAGE_DOCUMENTS`, i.e. the mechanism is used elsewhere in the same manifest). Code, from `dexdump -d` of `classes.dex`: `openFile` calls `getPath(uri)`; a null path throws `RuntimeException("Unsupported URI")`, otherwise `new File(path)`, and when the file does not exist it is created if `mode.contains("w")` (else `FileNotFoundException`), after which `ParcelFileDescriptor.open(f, ParcelFileDescriptor.parseMode(mode))` opens it - so the caller chooses both the absolute path and the access mode; `getPath` accepts only URIs whose authority equals the literal above and whose path is `FS/<base64url(absolute directory)>/<name>` (`Base64.decode(..., URL_SAFE|NO_PADDING|NO_WRAP)` then `Utils.mbAddSl(dir) + name`), and `canProvide` does nothing but compare that authority string. There is no caller check anywhere in the class (grep for `getCallingPackage`/`checkCalling*`/`Binder.getCallingUid` over the dumped class: none). Pass 1 (emulator-5554, cve_fresh33, API 33; attacker `com.cvefind.probe2`, uid 10294, INTERNET only; victim uid 10177): CONTROL - the probe reading the target path itself gives `selfRead exists=false canRead=false len=0` / `open failed: ENOENT`, and `adb shell ls -l /data/data/com.ghostsq.commander/files/PROBE-PROOF.txt` gives `Permission denied`; ARM A - one `openOutputStream` through the provider logs `WRITEURI content://com.ghostsq.commander.FileProvider/FS/L2RhdGEvZGF0YS9jb20uZ2hvc3RzcS5jb21tYW5kZXIvZmlsZXMv/PROBE-PROOF.txt -> wrote 32 bytes`; ARM B - the same URI through the provider logs `READURI... -> 32 bytes: PROBE-WROTE-INTO-GC-PRIVATE-1111`. Pass 2 (emulator-5558, cve_fresh33_3, API 33; attacker `com.cvefind.probe`, uid 10254, its own build and install; victim uid 10178, reinstalled from the same hash-verified APK): same control (`ENOENT` + shell `Permission denied`), then `WRITEURI... -> wrote 19 bytes` and `READURI... -> 19 bytes: PASS2-GC-WRITE-1125`; the pass-2 log lines carry the tag `PROBE2` only because that string is a leftover constant in the probe source - the package that ran is `com.cvefind.probe` (uid 10254), as the `am start -n com.cvefind.probe/.ProbeActivity` command and the `dumpsys` uid line in the same log show.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation; the caller needs the authority literal and, on Android 11+, visibility of the target package, which a free manifest declaration provides.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable code path is unchanged on the default branch commit that was checked. Recommended remediation: canonicalise the caller-supplied path and confine it to the intended directory before opening it, and validate the identity of the caller rather than trusting a normal-level permission.
