## Summary

ShowCase (com.wirelessalien.android.moviedb) version 49 for Android: OAuth redirect handler with no `state` and no PKCE: the attacker's authorization code becomes the victim's Trakt session, stored unattended in default SharedPreferences Named next step (cheapest first): a real smali/jadx rebuild that rewrites the token endpoint to a lab mock — byte patching the string table is not viable (ART rejects out-of-order `string_ids`) — then one arm proving 'attacker code -> token stored -> subsequent sync leaves the device toward the attacker account'. Alternative worth pricing first: check whether the app has any configurable API base (a debug/shared preference) before rebuilding; if neither works on an emulator, the row caps at 'unattended spend of an attacker-supplied code' and that is likely below this project's floor

## Attack vector and prerequisites

Any app can deliver the redirect URI to the exported activity (the second, `com.wirelessalien.android.moviedb://callback` scheme is open as well). No runtime permission and no user interaction beyond the victim app being alive. Precondition: the attacker must first obtain a valid authorization code for the victim app's `client_id` through the standard `/oauth/authorize` flow, i.e. by logging in once with an account the attacker controls.

## Proof of concept

Environment: API 33 emulator, `uid=2000(shell)` asserted before and after every zero-permission action; root used only to read prefs ground truth. - Arm A, shipping APK (entry reachability, no mock, no network): a zero-permission probe (`com.rv2.w6h703probe`, no requested permissions) delivering `trakt.wirelessalien.showcase://callback?code=RV2-ATK-CODE-4921` reaches the handler - the victim logs `URI received: trakt.wirelessalien.showcase://callback?code=RV2-ATK-CODE-4921` and then attempts the exchange (`E MainActivity: Error:` with the real `api.trakt.tv` unreachable offline); root prefs show no `trakt_*` keys. The second scheme routes the same way. So the unauthenticated handler entry and the spending of a caller-supplied code are provable on the shipping artifact. - Arm B, lab rebuild (the token endpoint redirected to a local mock; the shipping build talks to the real `api.trakt.tv`): the probe delivers the same code to the warm app; the mock receives `POST /oauth/token` with `code=RV2-ATK-CODE-4921` and the victim's bundled `client_id`/`client_secret`, and root ground truth shows the victim's prefs file holding `<string name="trakt_access_token">MOCK-AC-RV2-ATK-CODE-4921</string>` and `<string name="trakt_refresh_token">MOCK-RT-RV2-ATK-CODE-4921</string>` - the attacker-supplied code became the victim's stored Trakt session, unattended. - Refresh leg (same rebuild): force-stop and relaunch -> `checkTokenExpiration` -> expired -> `POST /oauth/token` with `grant_type=refresh_token` using the attacker-minted refresh token -> rotated tokens stored. The attacker-minted session self-sustains. - Controls: delivering the callback with no code yields `Authorization code not found in the redirect URI` and zero token requests; delivering a wrong code yields `400 invalid_grant` and unchanged prefs. Pattern control: the sibling TMDB leg binds the callback to a locally stored `request_token` and ignores the URI-supplied value - the safe pattern - so the Trakt leg's total absence of binding is the anomaly, not a codebase-wide habit.

## Impact

Attacker can exploit without user interaction - Trust boundary crossing from untrusted app to victim app UID - Affects confidentiality/integrity of victim app data

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond the application being alive; the OAuth callback is delivered to it.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.

## Prior art

NVD, OSV and the upstream project's advisory and issue trackers were queried for this package and mechanism at verification time: no matching entry was found, and the upstream code still ships the same declaration where it was checked.
