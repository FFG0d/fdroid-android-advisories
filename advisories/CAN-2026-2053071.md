# Exported headless activity in Download Navi overwrites the system clipboard with caller text

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053071` |
| **Package** | `com.tachibana.downloader` |
| **Product** | Download Navi |
| **Affected versions** | 15 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H35-01 |

## Summary

Download Navi (com.tachibana.downloader) version 15 for Android: an exported permission-less *headless* activity that writes caller-supplied text straight into the device's system clipboard, with no confirmation and no caller check Impact ceiling: Ceiling: the primitive is a *write* - no read of a pre-existing clip, no code execution and no privilege escalation are claimed; the attacker controls the text but not the clip's MIME label (that is `intent.getType`). Impact as measured: a zero-permission app silently replaces the user's clipboard, so the user's next paste into whatever app they are using (terminal, password manager, chat) carries attacker content

## Attack vector and prerequisites

Precondition: none beyond installation - no preference gate, no account, no SAF grant and no first-run wizard,

## Proof of concept

Artifact read with `aapt2 dump xmltree` on the very APK that was installed: the component is `android:exported="true"` (an explicit export - the app targets API 31, so this is deliberate), has no `android:permission`, and is `Theme.NoDisplay`, so it never draws a window and the user has nothing to see or decline. `SendTextToClipboard.java:38-62`: `onCreate` takes `Intent.EXTRA_TEXT` (`:45`, `:49`), builds `ClipData.newPlainText(intent.getType, text)` (`:51`) and calls `clipboard.setPrimaryClip(clip)` (`:52`) before `finish` (`:60`) - no `getCallingPackage`, no uid/signature test, no confirmation, no configuration gate; the only user-visible artefact is a Toast (`:54-57`). That the write lands at all depends on this component being *started* by the attacker and therefore focused: since Android 10 a background app may not write the primary clip, and pass 1/pass 2 both ran with the launcher in the foreground. Pass 1 (emulator-5558, cve_fresh33_3, API 33; attacker `com.cvefind.probe`, uid 10218, INTERNET only): baseline read by the probe as a foreground app `CLIP empty`; the explicit SEND produced `ActivityTaskManager: START u0 {act=android.intent.action.SEND typ=text/plain cmp=com.tachibana.downloader/.ui.SendTextToClipboard clip={text/plain {T(16)}} (has extras)} from uid 10218`; read back `CLIP item[0]=CDP-CLIP-052523`. Control A - the identical SEND with no `EXTRA_TEXT` - left the clipboard byte-identical (`CDP-CLIP-052523`, same `hasLabel... 05:25:24` timestamp), so the write is driven by the extra and not by the launch. Control B (positive) - a second SEND carrying a different marker replaced the clip with `CDP-CLIP2-052601`, i.e. the content is caller-chosen; a third run reproduced it end to end (`CDP-CLIP3-052902` -> read back unchanged). Pass 2 (emulator-5560, cve_fresh33_4; attacker `com.cvefind.probe2`, uid 10178, own build/install, victim re-installed from the same hash-verified APK): `CLIP empty` -> `START u0 {... cmp=com.tachibana.downloader/.ui.SendTextToClipboard...} from uid 10178` -> `CLIP item[0]=CDP2-CLIP-052649`, and again `CDP2-CLIP2-052933`.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation - no preference gate, no account, no storage grant, no first-run wizard.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
