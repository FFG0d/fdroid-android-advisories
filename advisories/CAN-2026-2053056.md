# Exported search activity in Focus Podcast fetches a caller URL and renders the response

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053056` |
| **Package** | `allen.town.focus.podcast` |
| **Product** | FocusPodcast |
| **Affected versions** | 70 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-F01 |

## Summary

FocusPodcast (allen.town.focus.podcast) version 70 for Android: SSRF with rendered response in Focus Podcast (allen.town.focus.podcast) v70, Android: the exported, permission-less `RssSearchActivity` passes a caller-supplied URL straight into the feed download path (`onCreate:103` -> `lookupUrlAndDownload` -> `startFeedDownload:217-231` builds the `Feed` from caller url/title/author/coverUrl, confirmed line-by-line in the official tarball), so a locally installed app makes the victim fetch an attacker-chosen URL with zero interaction; the fetched response is then parsed and rendered in the victim's UI, giving the attacker a read-back oracle, and the fetched feed is persisted in the victim's database. Impact ceiling: A locally installed app can, with no user interaction, make the victim fetch an attacker-chosen URL (SSRF reachable into the device loopback and private networks) and observe the fetched content rendered in the victim's UI - a read-back oracle via which a listener on `127.0.0.1` or a private-network host can be probed and its responses distinguished (measured: different ports render different marker sets); the fetched feed is persisted in the victim's database and survives after the attacking listener is gone. Ceiling: network reachability + rendered-response oracle + persistence; no code execution, no direct file theft (local-scheme loads were refuted as attacker-visible impact), and no confidentiality breach beyond what the rendered response reveals are claimed.

## Attack vector and prerequisites

Any app can start the exported activity with a URL of its choosing (explicitly or through the exported `VIEW`/`BROWSABLE` filters, so a web link works too). No runtime permission and no user interaction beyond the attacker-driven start. The URL must be fetchable by the victim - here an attacker host on loopback (`10.0.2.2` from the device), i.e. a private-network target.

## Proof of concept

Attacker: own zero-permission probe (`com.rv2.f01probe`, uid 10175; only the platform's POST_NOTIFICATIONS appears, `granted=false`); `uid=2000(shell)` asserted before and after the zero-permission steps; two attacker HTTP servers on host ports 8124 and 8133 serving distinct marker sets; `adb reverse --list` empty before and after, so the victim reached the attacker directly. - Receipt: the victim's fetch of the probe-supplied URL is receipted in the attacker's log (`GET /feedA.xml HTTP/1.1 200`), matching the device-side chain `OnlineFeedViewActivity: feed url ...` -> `DownloadService: got request ...` -> `HttpDownloader: response code 200` -> `download successful` -> `DBTasks: Found no existing Feed with title RV2T-TLA7Q. Adding as new one.` - Rendered response: the victim UI shows only the markers served by the attacker's feed - title, author, description, feed-URL row and an episode row (resource ids `txtvTitle`, `txtvAuthor`, `description`) - with no extras passed by the probe. - Response oracle: the identical trigger against port 8124 renders marker set A exclusively and against port 8133 renders set B exclusively, so the victim UI reflects the exact bytes served at the caller-supplied URL. - Persistence: root-read of the victim's private database (`databases/focusPodcastApp.db`) shows a feeds row with the attacker's title/description/author and the attacker's URL as `rss_url`, plus an episodes row. With both attacker listeners stopped, a force-stop and relaunch through the same URL renders the same markers from persisted state, and the relaunch log contains no download lines - a DB replay, not a new fetch. - Controls: a `ftp://` URL is normalized to `http://ftp://...` and never reaches a listener (feed count stays 0); an explicit launch with no action/data/extra logs `OnlineFeedViewActivity: feedUrl is null.` and downloads nothing. - One report claim stays withdrawn: "an attacker-authored feed is surfaced as a subscription without the upstream confirmation step" was NOT reproduced - the injected row is stored with `is_subscribed=0`, so the measured effect is content/DB injection and rendered SSRF, not a subscription-list entry.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation of the application.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
