# Exported activity in CodeCatcher persistently enables its shipped-disabled debug component

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053068` |
| **Package** | `co.ec.cnsyn.codecatcher` |
| **Product** | CodeCatcher |
| **Affected versions** | 131 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H23-01 |

## Summary

CodeCatcher (co.ec.cnsyn.codecatcher) version 131 for Android: an exported permission-less activity whose DEBUG action persistently enables the app's shipped-disabled debug component, and any app can then launch the internal log UI it exposes Impact ceiling: Ceiling, stated: no attacker-readable return channel is claimed - the debug UI renders logs to the screen and the attacker cannot read pixels or tap, and this package ships no exported provider through which the same data could be read back; the claim is the unattended persistent component-state change on a shipped-disabled component plus the foreground reachability of that internal surface, which is the class granted as state injection in `W5-31` / `W6-H13-02` / `W6-H12-01`. The exported `androidx.compose.ui.tooling.PreviewActivity` in the same package is noted and NOT part of this finding

## Attack vector and prerequisites

Any app can start the exported, permission-less activity with its DEBUG action, which persistently enables the app's shipped-disabled debug component; the same or any app can then launch the internal log UI that this exposes. No runtime permission and no user interaction. Reach it by explicit component - the implicit DEBUG startup is not the reachable form on API 33.

## Proof of concept

Shipped manifest: `DebugActivity` is declared `android:enabled="false"` (deliberately unshipable) and `exported="true"`; `ActionActivity` is `exported="true"` with no `android:permission` and an intent-filter for `co.ec.cnsyn.codecatcher.DEBUG`. `ActionActivity.kt:25-52` reads `packageManager.getComponentEnabledSetting(DebugActivity)` and flips it - `setComponentEnabledSetting(..., COMPONENT_ENABLED_STATE_ENABLED, DONT_KILL_APP)` plus `settings.putBoolean("debug-enabled", true)` in one branch, `..._DISABLED` in the other, then `finish` - with no caller check, no confirmation and no user-visible signal; the branch is chosen by the state the attacker drives, so the primitive is two-way. `DebugActivity.kt:61-90` then renders the app's internal diagnostic tabs `Crash` / `Service` / `Service Day` / `App Logs` over its own `database.servicelog.ServiceLog` rows - the log of the SMS/OTP capture service this app exists for. Pass 1 (emulator-5556, uid=2000, no root, `Active default network: none`, attacker `com.cvefind.probe`): baseline `am start.../.DebugActivity` -> `Error type 3... does not exist` (a disabled component is absent from the resolver, which is also why `dumpsys package` does not list it); control `ACTION=conflict-free non-DEBUG action co.ec.cnsyn.codecatcher.HISTORY` to the same activity -> unchanged `Error type 3`; then `ACTION=co.ec.cnsyn.codecatcher.DEBUG` from the zero-permission probe -> the same `am start` succeeds, with `ActivityTaskManager: START u0 {flg=0x10000000 cmp=co.ec.cnsyn.codecatcher/.DebugActivity} from uid 2000`; the probe then launches `DebugActivity` itself (focus `co.ec.cnsyn.codecatcher/co.ec.cnsyn.codecatcher.DebugActivity`, UI shows `No Crash Yet` plus the four tabs); a second identical call returns it to `Error type 3`. Pass 2 (emulator-5558, attacker `com.cvefind.probe2`, own build/install) reproduced all five arms identically (baseline disabled, non-DEBUG untouched, DEBUG enables, probe2 launches the UI, second DEBUG disables)

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation of the application.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
