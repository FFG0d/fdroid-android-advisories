# Exported activity in neutriNote CE autosaves caller text into a caller-chosen content URI

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053057` |
| **Package** | `com.appmindlab.nano` |
| **Product** | neutriNote CE |
| **Affected versions** | 1387 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H1-05 |

## Summary

neutriNote CE (com.appmindlab.nano) version 1387 for Android: caller-supplied absolute content URI is opened for write by the app's own default-on autosave, with caller-supplied text appended

**Vulnerable component:** `com.appmindlab.nano.DisplayDBEntry` exported=true, no permission, no intent-filter (explicit-component launch), launchMode=singleTask

## Attack vector and prerequisites

Any app can launch the activity by class name, supplying `EXTRA_URI` (an absolute content URI) and the shared-content text. No runtime permission, no user interaction, no prior state. Two preconditions, measured: autosave must be left at its default (on), and the write succeeds for documents the victim itself can write - the launch is what arms it, and the attacker's own write to the same document fails.

## Proof of concept

Environment: API 33 emulator; victim installed (versionCode 1387, targetSdk 36); probe with no requested/install/runtime permissions running as uid 10175 against victim uid 10174; `uid=2000(shell)` asserted before and after every action, root used only to read ground truth and to edit one preference fixture. Reachability: each attack launch left `topResumedActivity = com.appmindlab.nano/.DisplayDBEntry`. - RUN 2 (create): the caller launched the editor with `EXTRA_URI = content://com.appmindlab.nano.provider/sdcard/Android/data/com.appmindlab.nano/files/RV2PWN.txt` (a non-existent file) and `EXTRA_SHARED_CONTENT = "RV2-ATTACKER-TEXT-run2"`. After the autosave window the file existed with size 22 - byte-exact the attacker's text - and **owner uid 10174, i.e. the victim**, mtime T+121 s after the launch. - RUN 3 (overwrite + append of a victim-owned file): the same call against the now-existing file rewrote it from 22 to 48 bytes as `RV2-ATTACKER-TEXT-run2\n\n\nRV2-ATTACKER-TEXT-run3\n`, owner unchanged - caller-driven overwrite with the attacker's bytes appended, matching the code path exactly (read leg, `setupSharedContent`, autosave rewrite). - CONTROL 1 (write is URI-driven): the same launch with no `EXTRA_URI` produced no file anywhere in the victim's external files directory after 150 s. - CONTROL 2 (gated by the default-on autosave): with `pref_auto_save=false` set on a stopped victim, the identical attack against a fresh target never created the file; the preference was restored afterwards.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: autosave left at its shipped default (on).

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
