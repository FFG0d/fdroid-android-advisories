# Exported activity in Shopping List imports a caller file and opens an attacker-authored list

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053078` |
| **Package** | `com.wbpxre150.shoppinglist` |
| **Product** | ShoppingList |
| **Affected versions** | 11.0 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H43-01 |

## Summary

ShoppingList (com.wbpxre150.shoppinglist) version 11.0 for Android: an exported permission-less activity that ingests a caller-supplied file straight into the user's own Room database and then navigates the victim's UI to the attacker-authored list, with no confirmation and no caller check (the comment on `:46` is `// Import the list`) Impact ceiling: Ceiling: write-only (the component cannot read the user's existing lists back to the caller) and not silent - the import screen *is* drawn (`Theme.ShoppingList`), so this is unattended injection plus foreground-UI hijack rather than a background write; the import adds a list, it does not rename, delete or overwrite one, and a name collision is uniquified by `generateUniqueName` (`:96-110`) as `NAME (n)` rather than replacing (visible as `...LIST2-091212`); no code execution, no privilege escalation, no data read-out. The control arms were recorded as logcat extracts (presence or absence of the victim's detail-activity entry), not as separate UI dumps - stated rather than papered over

## Attack vector and prerequisites

Precondition: none beyond installation - no account, no first-run wizard, no preference gate, no storage or SAF grant, no victim interaction; the payload channel is entirely attacker-owned. Standing caveat for this shape: the caller must be allowed to start an activity (Android 10+ background-activity-start rule), satisfied in both passes by firing from the probe activity while it held the foreground

## Proof of concept

Reporter-verified proof of concept, reproduced on a stock Android 13 (API 33) emulator cold-booted with -wipe-data. The attacker is an application installed on the same device holding no runtime permissions; the victim is the shipped build under test. Prerequisites: Precondition: none beyond installation - no account, no first-run wizard, no preference gate, no storage or SAF grant, no victim interaction; the payload channel is entirely attacker-owned. Standing caveat for this shape: the caller must be allowed to start an activity (Android 10+ background-activity-start rule), satisfied in both passes by firing from the probe activity while it held the foreground Artifact read with `aapt2 dump xmltree --file AndroidManifest.xml` on the installed APK: `ImportListActivity` is `android:exported="true"` (explicit), no `android:permission`, `android:theme` `0x7f0f0278` = `style/Theme.ShoppingList` (parent `Base.Theme.ShoppingList` -> `Theme.Material3.DayNight`), and the `SEND` filter's mime is `application/x-shoppinglist`. `ImportListActivity.kt:27-38` takes `intent.data` for `ACTION_VIEW` or `intent.getParcelableExtra(Intent.EXTRA_STREAM, Uri:class.java)` for `ACTION_SEND`; `:40-44` bounces only when the URI is null; `:47` calls `importList(fileUri)` directly, with no `getCallingPackage`, no uid/signature test, no dialog and no button. `importList` (`:64-131`) reads the URI through the app's own `ContentResolver` (`ListImportService.kt:36`), `gson.fromJson(..., ExportShoppingList:class.java)` (`:45`), validates only `listName.isNotBlank` (`:55`) and `version <= 1` (`:60`), then `repository.importList(list, items)` (`:90`) writes the rows and `:116-121` starts `ShoppingListDetailActivity` + finishes. The attacker's payload never has to be a file either app can reach: the caller supplies its own `content://` URI in `EXTRA_STREAM` plus `FLAG_GRANT_READ_URI_PERMISSION`, so this needs no SAF grant and no storage permission (unlike `W6-H34-01`). Wire format (`models/ExportModels.kt:8-37`): `{version, exportTimestamp, listName, items:[{name, quantity, price, position}]}`. Pass 1 (emulator-5554, cve_fresh33, API 33; attacker `com.cvefind.probe2`, uid 10294, INTERNET only, zero install permissions): baseline UI = `MainActivity` with no lists; ATTACK 1 (explicit `SEND typ=application/x-shoppinglist`, `EXTRA_STREAM` = the attacker's own provider URI, `grants=1`) logged `ActivityTaskManager: START u0 {act=android.intent.action.SEND typ=application/json flg=0x10000003 cmp=com.wbpxre150.shoppinglist/.ImportListActivity clip={application/json {U(content)}} (has extras)} from uid 10294` immediately followed by `START u0 {cmp=com.wbpxre150.shoppinglist/.ShoppingListDetailActivity (has extras)} from uid 10296` (the victim's own uid), and the UI dump then read `text="SHLIST-ATTACKER-LIST-091102"`, `text="SHLIST-ITEM-091102"`, `text="$1.00"`. CONTROL A (the same `SEND` with no `EXTRA_STREAM`) and CONTROL B (`EXTRA_STREAM` serving bytes that are not a shopping list) each recorded only the `ImportListActivity` entry and no `ShoppingListDetailActivity` entry - per `:40-44`/`:133-139` and `ListImportService.kt:44-48` those are the `showError` and `Invalid file format` arms, i.e. no write; ATTACK 2 with a fresh marker read back `text="SHLIST-ATTACKER-LIST2-091212"` / `text="SHLIST-ITEM2-091212"`. Pass 2 (emulator-5558, cve_fresh33_3, API 33; attacker `com.cvefind.probe`, uid 10218, own build and install, victim reinstalled from the same hash-verified APK): baseline no lists, ATTACK 1 from uid 10218 followed by the victim uid 10249 starting its own `ShoppingListDetailActivity`, UI read `text="SHLIST-P2-LIST-091328"` together with `text="SHLIST-P2-ITEM-091328"` and 3 items at `$2.50`/`$7.50`, CONTROL (no `EXTRA_STREAM`) ImportListActivity only, ATTACK 2 `text="SHLIST-P2-LISTB-091347"` / `text="SHLIST-P2-ITEMB-091347"`. ## Impact

Ceiling: write-only (the component cannot read the user's existing lists back to the caller) and not silent - the import screen *is* drawn (`Theme.ShoppingList`), so this is unattended injection plus foreground-UI hijack rather than a background write; the import adds a list, it does not rename, delete or overwrite one, and a name collision is uniquified by `generateUniqueName` (`:96-110`) as `NAME (n)` rather than replacing (visible as `...LIST2-091212`); no code execution, no privilege escalation, no data read-out. The control arms were recorded as logcat extracts (presence or absence of the victim's detail-activity entry), not as separate UI dumps - stated rather than papered over

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation - no account, no first-run wizard, no preference gate, no storage grant.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
