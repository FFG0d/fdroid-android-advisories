# Exported headless activity in Share2ArchiveToday overwrites the system clipboard with a caller URL

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053072` |
| **Package** | `org.gnosco.share2archivetoday` |
| **Product** | Share 2 Archive Today |
| **Affected versions** | 61 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H36-01 |

## Summary

Share 2 Archive Today (org.gnosco.share2archivetoday) version 61 for Android: an exported permission-less *headless* activity that overwrites the device's system clipboard with a caller-supplied URL, with no confirmation, no caller check and nothing drawn on screen Impact ceiling: Ceiling: write-only - the component cannot read a pre-existing clip; the attacker cannot choose the clip label ("Cleaned URL", set by the app) and the app rewrites the URL through its own cleaner, so the clipboard ends up with the cleaned form rather than the raw string; no code execution and no privilege escalation are claimed. Impact as measured: a zero-permission app silently replaces the user's clipboard, so the user's next paste carries attacker content

## Attack vector and prerequisites

Precondition: none beyond installation - no account, no preference gate, no SAF grant, no wizard

## Proof of concept

Artifact read with `aapt2 dump xmltree` on the installed APK: `ClipboardActivity` is `android:exported="true"` (explicit), has no `android:permission` and is `Theme.NoDisplay`. `MainActivity.kt:56-73` (`handleShareIntent`) takes `ACTION_SEND` + `text/plain`, reads `Intent.EXTRA_TEXT` (`:63`), extracts a URL (`:64`) and calls `fourSteps(url)` (`:67`) with no caller check and no confirmation; `ClipboardActivity.kt:11-15` overrides `threeSteps` to `processArchiveUrl` -> `handleURL` -> `copyToClipboard`, and `copyToClipboard` (`:17-28`) does `ClipData.newPlainText("Cleaned URL", url)` + `clipboard.setPrimaryClip(clip)` then `finish`; `openInBrowser` (`:30-33`) is overridden to copy as well, so the component's entire purpose is to put caller text on the clipboard while showing nothing. The write lands because the attacker *starts* this activity, so it holds the window focus (since Android 10 a background app may not write the primary clip). Pass 1 (emulator-5562, cve_fresh33_5, API 33; attacker `com.cvefind.probe2`, uid 10178, INTERNET only): baseline clip `https://second.example.org/x/S2AT2-055233` (label `hasLabel(11)`); the attack `EXTRA_TEXT=https://p1.example.org/x?utm_source=S2AT-P1-055333` produced `ActivityTaskManager: START u0 {act=android.intent.action.SEND typ=text/plain cmp=org.gnosco.share2archivetoday/.ClipboardActivity clip={text/plain {T(50)}} (has extras)} from uid 10178`; read back `CLIP item[0]=https://p1.example.org/x` - the `utm_source` the app strips is gone, so the clip content is demonstrably produced by this app from the caller's text. Control - the same SEND whose body contains no URL - left the clipboard unchanged (same `hasLabel... 05:53:40.756`). A second positive attack with a different URL (`.../x/S2AT2-055233`) also replaced the clip. Pass 2 (emulator-5560, cve_fresh33_4; attacker `com.cvefind.probe`, uid 10180, own build/install): baseline `https://p2.example.net/a` -> `START u0 {... cmp=org.gnosco.share2archivetoday/.ClipboardActivity...} from uid 10180` -> `https://p2b.example.net/y`, control unchanged.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation - no account, no preference gate, no storage grant, no wizard.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
