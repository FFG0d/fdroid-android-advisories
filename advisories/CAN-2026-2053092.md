## Summary

OMN-Go (net.basov.omngo.fdroid) version 26080824 for Android: loopback-equates-owner in the embedded Go HTTP server: `middleware.go:10-15 isLocalConnection` reads only `r.RemoteAddr`, and `middleware.go:128-131 hasRole` grants the admin role on that basis, so every admin route is open to any local process; `/api/note` and `/api/search` carry no `authMiddleware` at all (`server.go:221,227`). `/api/sql` is code-reachable through the same unauthenticated admin router, but on the test guest its execution is blocked by a seccomp artifact (the victim process aborts with SIGSYS), so its effect is treated as unverified in this request. Impact ceiling: A locally installed app holding only the INTERNET permission can, with no user interaction, read the victim's entire note corpus via `/api/search` and `/api/note`, read and write notes through the unauthenticated admin routes (`/api/save`, `/api/newpage`, `/api/status`), and obtain the admin password in cleartext via `/api/config`. Ceiling: effects are confined to the victim app's own data (its notes and its configuration) reachable through these HTTP endpoints; confidentiality and integrity of that data are both affected. Not claimed: code execution, access beyond the victim app's own data, and the effect of `/api/sql` (code-reachable but blocked at runtime by a seccomp artifact on the test guest - treated as unverified).

## Attack vector and prerequisites

An app holding only the INTERNET permission starts the exported, permission-less `MainActivity`, which brings up the app's own loopback HTTP server, then reaches the admin routes as a 'local' client. No user interaction and no prior state; the attacker app must declare INTERNET (an otherwise permissionless socket connection is blocked on API 33).

## Proof of concept

Zero-permission app reaches `http://127.0.0.1:8081/api/search` (port corrected 11:21 during preparation: the F-Droid artifact binds 8081, not 8080 — `build.gradle:68`, `doc/API.md:25`; the harness resolves it on device) + `/api/note?name=` (full note corpus read, no interaction) and the admin set `/api/save`, `/api/newpage`, `/api/config`, `/api/sql`, `/api/db/restore`, `/api/status` (`server.go:217-255`); Android gives apps a shared loopback, no `SO_PEERCRED`/UID check anywhere. Device plan + decisive control; Prep-lane additions: an extra limb — `GET /api/config` returns the `admin_password` in cleartext (redaction is built into the server, not the caller); and the *client identity* constraint the verdict must respect: only the attacker-APK arms (`HttpURLConnection`, own uid, 0 permissions vs an INTERNET-only sibling) support "zero-permission app", while the `adb shell`/adbd arm (uid 2000) is labelled weaker in its own log header and may not carry the impact claim.  pass-1 evidence, harness fixes logged in, prior art appended in (upstream HEAD still carries the predicate; no identifier cited that was not retrieved); pass 2 re-ran the arms independently (slot released 14:42Z, `id` asserted uid=2000 throughout); Lead novelty re-check (15:45): web search naming OMN-Go + localhost trust + `admin_password` + unauthenticated config -> nothing relevant (0 hits for the project or the mechanism); consistent with the lanes' NVD/OSV/GitHub queries, all zero. Novelty holds for this app and this predicate

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation; attacker side holds only the INTERNET permission and needs no user interaction.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
