# Exported import activity in OpenTracks writes caller-served GPX KML KMZ data into the location database

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053065` |
| **Package** | `de.dennisguse.opentracks` |
| **Product** | OpenTracks (Non-reproducible) |
| **Affected versions** | 6751 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H14-14 |

## Summary

OpenTracks (Non-reproducible) (de.dennisguse.opentracks) version 6751 for Android: exported import door that parses a caller-served file and writes its contents — attacker-chosen tracks, times and coordinates — into the victim's own location database with no tap and no confirmation

**Vulnerable component:** 9 exported permission-less components of 45: `io.file.importer.ImportActivity` (exported=true, no `android:permission`, VIEW and SEND and SEND_MULTIPLE with schemes `file,content,data` and mime `application/gpx+xml,ap [...] thDataSdkService` (exported, no permission); the `data.ShareContentProvider` is exported=false grantUriPermissions=true

## Attack vector and prerequisites

Any app can send `ACTION_SEND` with the correct MIME (`application/gpx+xml` and friends) and `EXTRA_STREAM` pointing at a URI served by its own ContentProvider; no component name is needed, the filter routes it. No runtime permission, no user interaction, no prior state. Do not route this through the app's `publicapi` gate - both of its flags default to off (`res/values/settings.xml:282`, `:284`), so that path is not the reachable one.

## Proof of concept

Environment: API 33 x86_64 emulator; shell asserted `uid=2000(shell)` before every action; probe `com.rv2.probe14` with zero requested/runtime permissions (uid 10175). Baseline: victim database pulled as root before any test - tracks=0, trackpoints=0. Attacker payload: a GPX served by the probe's own `GpxProvider` with track name `RV2W6H1414-T1-MAIN-MARKER-20260925`, description `rv2reverify-unique-desc-1337`, `<trackid>` UUID `1f2e3d4c-5b6a-4718-9900-aabbccddeeff` and three trackpoints with chosen coordinates/elevations/timestamps. - T1 (main): the probe starts the victim with `ACTION_SEND`, type `application/gpx+xml`, `EXTRA_STREAM` = probe URI, `FLAG_GRANT_READ_URI_PERMISSION`. AMS logs `START u0 {... cmp=de.dennisguse.opentracks/.io.file.importer.ImportActivity clip={application/gpx+xml {U(content)}}} from uid 10175`; the victim's WorkManager runs `ImportWorker` -> `Worker result SUCCESS`. Root-pulled database: 1 track whose name, description and uuid bytes are byte-exact the attacker's values, with `time_start=1790330400000` (= the attacker's 2026-09-25T10:00:00Z) and 3 trackpoints carrying the attacker's lat/lon/elevation/time. The whole flow ran headless - the only UI is the progress screen, which appears while the import already runs. - T2 (control, SEND with no URI): the activity starts but NPEs at `ImportActivity.java:92`, `ImportWorker` never runs, database unchanged. - T3 (control, wrong file type): `text/plain` file -> `ImportWorker: Unsupported file format.` -> `Worker result FAILURE`, database unchanged (the gate is filename-extension only). - T4 (control, implicit SEND with wrong MIME): AMS routes to the system `ResolverActivity`, the victim is never invoked, database unchanged.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: none beyond installation; the activity is reached through its MIME filter, so no component name is needed.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
