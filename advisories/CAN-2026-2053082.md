# Exported activity in MotionUI loads a caller URL and injects stored credentials into that page

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053082` |
| **Package** | `app.motionui.android` |
| **Product** | Motion-UI |
| **Affected versions** | 101 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H5-09 |

## Summary

Motion-UI (app.motionui.android) version 101 for Android: cross-app credential disclosure: an exported, permission-less activity takes a caller-chosen URL extra and loads it in a JavaScript-enabled WebView (`MainActivity.java:83` -> `:273`), after which the app injects the victim's stored username and password into that page's DOM and auto-submits the form (`:154-155`, `:163-170`), so the credentials are handed to an attacker-chosen origin with no user interaction Impact ceiling: A locally installed app with no permissions can, with no user interaction, have the victim load an attacker-chosen URL in its JavaScript-enabled WebView; the victim's stored username and password are then injected into that page and the form is automatically submitted, delivering the credentials to the attacker's origin unattended (measured: collector received the submitted username and password; 4 cross-origin script executions in the victim's WebView). The stored credentials also remain readable in plaintext in the app's own logs (`motionUIEncryptedSharedPreferences.java:47`). Ceiling: credential disclosure to the attacker-chosen origin and script execution inside the victim's WebView; no code execution outside the WebView and no access beyond the credentials and WebView content are claimed.

## Attack vector and prerequisites

Any app can start the exported activity with a URL of its choosing. No runtime permission, no user interaction. Precondition, minimal: the victim must have stored credentials, which is exactly what the app's own login flow does; cleartext traffic is enabled in the manifest, so the attacker page need not be HTTPS.

## Proof of concept

Environment: a fresh instance booted after the earlier dispatch conflict was resolved; `adb root`/`unroot` normalized and `uid=2000(shell)` asserted before and after every phase; probe `com.rv2.w609probe` built locally with an empty permission list (uid 10175); ground truth read as root from the victim's `shared_prefs`. - Fixture: marker credentials (`rv2h9user9d1f` / `rv2h9pass7c2a`) were stored through the victim's own code path - a hosted page whose form the victim's own submit hook captured, producing EncryptedSharedPreferences entries (the app's designed storage path; no verifier code touches the store). - P (positive): the zero-permission probe starts `app.motionui.android/.MainActivity` with an attacker URL (`START u0 {cmp=app.motionui.android/.MainActivity (has extras)} from uid 10175`). The victim loads the page and, in the device's own log, reads the stored secrets (`Getting value rv2h9user9d1f from shared preferences`), while the attacker host records six exfiltration hits carrying the exact stored markers (`GET /marker?u=rv2h9user9d1f&p=rv2h9pass7c2a`), repeated as the page re-sends on timers. - N1 (control, credentials cleared): the beacons arrive with empty values and the device log has zero "Getting value" lines. - N2 (control, page without injection targets): the victim still reads both values, but the page beacon reports `NO-U-ELEMENT`/`NO-P-ELEMENT` - the secrets do not leave the WebView when the attacker page has no `[name=username]`/`[name=password]` fields. With P as the single-variable contrast, this shows the effect needs both the victim's stored credentials and the victim's own injection into the attacker origin. - The same bridge also lets any loaded origin overwrite the stored credentials (the write-back leg is the app's storage mechanism).

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: stored credentials present, which the application's own login flow produces.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
