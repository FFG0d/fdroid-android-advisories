# Exported activity in MotionUI loads a caller URL and injects stored credentials into that page

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053082` |
| **Package** | `app.motionui.android` |
| **Product** | Motion-UI |
| **Affected versions** | 101 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H5-09 |

## Summary

Motion-UI (app.motionui.android) version 101 for Android: cross-app credential disclosure: an exported, permission-less activity takes a caller-chosen URL extra and loads it in a JavaScript-enabled WebView (`MainActivity.java:83` -> `:273`), after which the app injects the victim's stored username and password into that page's DOM and auto-submits the form (`:154-155`, `:163-170`), so the credentials are handed to an attacker-chosen origin with no user interaction Impact ceiling: A locally installed app with no permissions can, with no user interaction, have the victim load an attacker-chosen URL in its JavaScript-enabled WebView; the victim's stored username and password are then injected into that page and the form is automatically submitted, delivering the credentials to the attacker's origin unattended (measured: collector received the submitted username and password; 4 cross-origin script executions in the victim's WebView). The stored credentials also remain readable in plaintext in the app's own logs (`motionUIEncryptedSharedPreferences.java:47`). Ceiling: credential disclosure to the attacker-chosen origin and script execution inside the victim's WebView; no code execution outside the WebView and no access beyond the credentials and WebView content are claimed.

## Attack vector and prerequisites

Any app can start the exported activity with a URL of its choosing. No runtime permission, no user interaction. Precondition, minimal: the victim must have stored credentials, which is exactly what the app's own login flow does; cleartext traffic is enabled in the manifest, so the attacker page need not be HTTPS.

## Proof of concept

Reporter-verified proof of concept, reproduced on a stock Android 13 (API 33) emulator cold-booted with -wipe-data. The attacker is an application installed on the same device holding no runtime permissions; the victim is the shipped build under test. Prerequisites: Vector: a locally installed app performs an explicit-component launch of `MainActivity` (exported, no permission, no intent-filter needed) with the `url` extra set to the attacker's page. Prerequisites: none beyond local app installation - the component is exported with no permission and applies no scheme/host check to the caller's URL (unlike the same app's in-app `Startup` path); no user interaction; the victim must have stored credentials in `motionUI_shared_preferences` for the credential-injection leg to fire, and the attacker page must be reachable over http/https (cleartext is permitted by `usesCleartextTraffic=true`). Static chain: census `exported="true"`, `permission`/`readPermission`/`writePermission` null, `filters: []` -> explicit-component launch by any app; confirmed against the hash-verified shipped APK (APK sha256 prefix `4078771c337ce418`; source tarball sha256 `3b10495d891cb0e8decf24b2f0620e91c8606eb7971cbdb55b2ff1257fb06c59`). Input: `MainActivity.java:83` `url = getIntent.getStringExtra("url");` -> sink `:273` `webView.loadUrl(url);` with no scheme/host check between them (the only test on `url` is `:196` `if (targetUrl.contains(url))`, which governs later navigations, not the first load - that asymmetry is the pattern control); enablers `:93` `setJavaScriptEnabled(true)`, `:112` `addJavascriptInterface(new MyJavaScriptInterface, "INTERFACE")`, `:117-121` third-party cookies. Effect leg: `:138-148` reads `motionUI_shared_preferences` (an `EncryptedSharedPreferences`, AES256_SIV/AES256_GCM, `motionUIEncryptedSharedPreferences.java:24-33`; plaintext also logged `:47`) then `:154-155` `view.evaluateJavascript("document.querySelector('[name=username]').value = '" + username + "';", null)` and the password twin - i.e. the secret is written into the attacker's page; `:163-170` additionally auto-submits the form. Write-back leg: `:41-66` `@JavascriptInterface processContent(username, password)` -> `encryptedSharedPrefs.set(...)`, callable from that same foreign origin, and because `:154-155` interpolate into a single-quoted JS literal with no escaping, attacker-planted values execute script in the origin of the next load (second-order, kept out of the headline). [...] Pass 2 re-ran the same arms on a second emulator with log-based assertions on the victim process: the collector received the submitted credentials (2 captured POSTs with the username field, 2 with the password field), the injected DOM state was observed (61 `Getting value` log lines from the victim's own value reads), and 4 cross-origin script-execution events fired from the attacker page in the victim's WebView. Control arms held: with a cleared victim and no attacker URL no injection occurs, and a page without a form throws instead of submitting. Upstream master was re-checked at the same source revision: `MainActivity.java` and `AndroidManifest.xml` still carry the identical declaration and code lines, so upstream remains unfixed. Prior-art queries (NVD, OSV, upstream issue tracker) found no entry for the Android wrapper: upstream GitHub issue #87 is the motion-UI web/server 6.x line (reported by an automated web-scanning service, maintainer: "Fixed in 6.0.0 & 6.0.1", PR #88), not the Android wrapper, which has its own version line (android-1.0.0/1.0.1); no CVE or GHSA exists for either line; issue #108 (uncaught exception on off-site links, fixed in android-1.0.1) is robustness only. Wording ceiling: the WebView class itself is not novel and is not claimed as such - the claim is this specific shipped code path plus the measured, unattended submission of the victim's stored credentials to an attacker-chosen origin.

## Impact

A locally installed app with no permissions can, with no user interaction, have the victim load an attacker-chosen URL in its JavaScript-enabled WebView; the victim's stored username and password are then injected into that page and the form is automatically submitted, delivering the credentials to the attacker's origin unattended (measured: collector received the submitted username and password; 4 cross-origin script executions in the victim's WebView). The stored credentials also remain readable in plaintext in the app's own logs (`motionUIEncryptedSharedPreferences.java:47`). Ceiling: credential disclosure to the attacker-chosen origin and script execution inside the victim's WebView; no code execution outside the WebView and no access beyond the credentials and WebView content are claimed.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: stored credentials present, which the application's own login flow produces.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.

## Prior art

NVD, OSV and the upstream project's advisory and issue trackers were queried for this package and mechanism at verification time: no matching entry for the Android wrapper was found, and upstream master still ships the same declaration and code lines where it was checked (the web/server 6.x issue #87 is a different code line and does not cover the Android path).
