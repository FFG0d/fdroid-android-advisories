# Exported device-admin activity in Shelter takes its HMAC key from the caller's Intent

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053061` |
| **Package** | `net.typeblog.shelter` |
| **Product** | Shelter |
| **Affected versions** | 445 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H12-01 |

## Summary

Shelter (net.typeblog.shelter) version 445 for Android: first-contact / key-enrolment primitive: the exported device-admin door whose only caller authentication takes its HMAC key from the very Intent it authenticates, so the first caller ever to reach a keyless instance names that key and then signs with it — not a general HMAC bypass

**Vulnerable component:** `net.typeblog.shelter.ui.DummyActivity` exported=true, no `android:permission`, launchMode=singleTask, one filter with the 13 custom actions, measured from a zero-permission caller process (uid 10214, `uses-permission` count 0 in its own `aapt dump badging`)

## Attack vector and prerequisites

Any app can start the exported activity with one of its actions and caller-supplied extras. No runtime permission and no user interaction. Precondition for the enrolment limb: the victim must be in its keyless (never-enrolled) state - a standing state on any device where Shelter has no resolvable other-profile instance, because the app cannot key itself without one. Once enrolled, the stored key must be presented, so this is a first-contact primitive, not a general HMAC bypass.

## Proof of concept

Environment: API 33 emulator; probe (`com.rv2.w6h12`, uid 10175) built in this pass from its own source with `uses-permission` count 0; victim uid 10174; every arm cold (`am force-stop` the victim, clear logcat, one action, observe) with `uid=2000(shell)` asserted before and after. Attacker-chosen keys K1/K2/K3. - B0 (baseline): single user, no device/profile owner, and the victim has no `shared_prefs` directory at all - keyless state established. - A1b (enrolment): the probe fires `UNINSTALL_PACKAGE` with `auth_key=K1` and a matching signature. The victim (uid 10174) starts `PACKAGEINSTALLER_CALLBACK` and the system uninstaller; root ground truth shows `shared_prefs/prefs.xml` now holding `<string name="auth_key">07c3adf6...d594</string>` - the attacker-named key, stored verbatim. A6 repeats the call cold with K1 and no key offered: accepted again, so the stored attacker key authenticates later calls. - A lab accident that sharpens the finding: an initial driver bug sent `auth_key` present-but-null. The victim accepted it and executed the uninstall, leaving prefs as `<map />` - the keyless branch accepts on the mere *presence* of the extra; not even a well-formed key is required. - A2 (preference escalation): a K1-signed `SYNCHRONIZE_PREFERENCE` with `name=cross_profile_file_chooser, boolean=true` writes that value and adds `net.typeblog.shelter.util.CrossProfileDocumentsProvider` to the package's `enabledComponents` - a shipped-manifest-disabled component becomes enabled, persisted. - A7 (binder escalation): a K1-signed `START_SERVICE` returns `resultCode=-1` with a live `BinderProxy` whose interface descriptor is `net.typeblog.shelter.services.IShelterService`; three read-only transactions are answered by the victim process. - Controls: the identical call signed with K2 is refused (prefs and `dumpsys` byte-identical); a call with no key and no signature is refused; on an already-enrolled instance, offering K3 changes nothing and K1 stays stored (the first-contact ceiling holds); a K1-signed call with a 61-second-old timestamp is refused; and a second valid call fired at the still-living instance produces no victim-side dispatch at all - `singleTask`/`onNewIntent` swallows it, which is why every measurement above was taken cold.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: for the enrolment limb, the instance must be in its keyless (never-enrolled) state - a standing state wherever the app has no resolvable other-profile instance.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
