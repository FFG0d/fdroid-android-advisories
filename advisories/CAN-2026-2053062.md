# Exported broadcast receiver in Tailscale changes VPN exit-node preferences without caller authentication

| | |
|---|---|
| **CVE ID** | *pending* — requested; MITRE CNA-LR tracking number `CAN-2026-2053062` |
| **Package** | `com.tailscale.ipn` |
| **Product** | Tailscale |
| **Affected versions** | 297862600 (affected) |
| **Weakness** | CWE-926 (Improper Export of Android Application Components) |
| **Platform** | Android |
| **Published** | 2026-10-11 |
| **Internal ID** | W6-H12-07 |

## Summary

Tailscale (com.tailscale.ipn) version 297862600 for Android: zero-permission broadcast that edits the victim's VPN policy inside the victim's own process -- the `/localapi/v0/prefs` handler is reached over an in-process `net.Pipe` ( correction: there is no socket, so the wider local-API surface is not attacker-reachable and must not be worded that way)

**Vulnerable component:** 4 exported permission-less components of 21: `MainActivity` (MAIN + `QS_TILE_PREFERENCES`), `ShareActivity` (SEND/SEND_MULTIPLE `*/*`), `androidx.compose.ui.tooling.PreviewActivity` (no filter) and `IPNReceiver` (exported=true, no `android:permission`, actions `com.tailscale.ipn.CONNECT_VPN`, `…DISCONNECT_VPN`, `…USE_EXIT_NODE`)

## Attack vector and prerequisites

Any app can send an explicit broadcast to `IPNReceiver` (or start `MainActivity` / `ShareActivity`). No runtime permission and no user interaction. Two bounded preconditions: the exit-node name must already exist in the victim's netmap (the attacker cannot introduce a new one), and the `CONNECT_VPN` leg on a fresh profile is gated by the system VPN consent - only the disconnect and prefs legs are unconditional. Upstream ships this as an intentional automation interface (Tasker use is discussed in its own issues), so the claim is the missing caller authentication and confirmation, not a hidden backdoor.

## Proof of concept

Environment: API 33 emulator; the shell held `uid=2000(shell)` at every step; all attacker actions were performed by a zero-permission probe (uid 10175). - T1 (positive): probe -> explicit broadcast `USE_EXIT_NODE` with `exitNode="" allowLanAccess=true`. Victim log: `LocalAPIRequest: Executing request:PATCH:/localapi/v0/prefs` then `gojni: EditPrefs: MaskedPrefs{ExitNodeID="" AutoExitNode="" InternalExitNodePrior="" ExitNodeAllowLANAccess=true}` - the attacker's value applied, no permission error in between. - T7 (bidirectional): the same with `allowLanAccess=false` -> `EditPrefs{...ExitNodeAllowLANAccess=false}`. The value tracks the extra both ways, with no validation. - T3 (disconnect leg): `DISCONNECT_VPN` -> `Worker result SUCCESS ... {StopVPNWorker, ipn-disconnect-vpn}`, and the backend logs a `[PATCH] /localapi/v0/prefs` (`WantRunning=false`) - the disconnect leg also performs a policy write with no consent. - T2 (connect leg): `CONNECT_VPN` -> `StartVPNWorker: Tailscale isn't ready to start the VPN, notify the user.` and `Worker result FAILURE` - gated exactly as stated above; no unconditional connect is claimed. - T6 (rejection + no return channel): `exitNode=rv2-nonexistent-peer` -> `Worker result FAILURE {UseExitNodeWorker, ipn-use-exit-node}` inside the victim process; the probe gets nothing back. - Control 1 (attribution): the same probe broadcasting to the victim's non-exported `MDMSettingsChangedReceiver` gets `SecurityException: Permission Denial: not allowed to send broadcast ... uid=10175` - the effects above are due to `IPNReceiver`'s exported-ness, not a generic broadcast hole. - Control 2 (no socket): TCP connects to 127.0.0.1:443/4191/44233 all refuse; `ss -tln` shows only adbd and `ss -xln | grep -i tailscale` is empty - corroborating the in-process `net.Pipe` design.

## Preconditions / configuration

Attacker: an application installed on the device with no runtime permissions. Victim: for the exit-node limb, an exit-node entry must already exist in the device's own netmap; the connect direction is consent-gated on a fresh profile.

## Remediation

No fix released by the upstream project as of 2026-09-27; the vulnerable declaration is unchanged on the default branch commit that was checked. Recommended remediation: add an android:permission (or set android:exported="false" where external callers are not intended) to the affected component so that only the vendor's own applications can reach it.
